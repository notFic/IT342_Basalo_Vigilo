EXECUTIVE SUMMARY

1.1 Project Overview

Vigilo is a streamlined digital registry designed to automate the tracking of visitor arrivals and departures within micro-to-small residential properties such as mini-studio rentals, dormitories, and bed space facilities. The system replaces traditional paper-based logbooks with a controlled web-based platform and native Android companion app, enabling security personnel to efficiently record visitor details including the specific host (tenant) being visited, monitor active guests in real-time, and process check-outs with accurate timestamping

1.2 Objectives

Design a responsive user interface that works consistently across web and mobile platforms

Develop a user-friendly digital logbook that replaces paper-based visitor records.

Implement secure Staff authentication using email and password credentials, as well as Google OAuth integration.

Provide a real-time dashboard displaying all active visitors and public security alerts.

Ensure Staff accountability by recording which specific user authorized each visitor entry.

1.3 Scope

Included Features:

Staff registration and authentication (Email/Password and Google OAuth)

Visitor entry form (Name, Contact, Host Name, Room Number, Purpose, Extended Visit).

System-generated arrival and departure timestamping.

File upload functionality to attach digital copies of Visitor IDs to their record.

Active visitor dashboard with Public Holidays API integration to warn guards of restricted building access days

Automated SMTP Email sending for account verification and Admin void notifications.

Search functionality for historical visitor records.

Responsive web interface and native Android application.

Excluded Features:

Hardware Barcode scanning integration.

Webcam photo capture for visitors.

Pre-registration portal for guests.

1.0 INTRODUCTION

1.1 Purpose

This document serves as the design specification for Vigilo. It outlines the functional requirements, core user journeys, and feature specifications to guide the development phase. This blueprint ensures that the core transactional logic (check-in and check-out) is clearly defined before implementation begins.

2.0 FUNCTIONAL REQUIREMENTS SPECIFICATION

2.1 Project Overview

Project Name: Vigilo
Domain: Facility Management / Security
Primary Users:

Property Managers / Caretakers

Security Guards

Problem Statement: Paper-based visitor logbooks in residential rentals (such as mini-studios, dormitories, and bed spaces) are difficult to search during security incidents, prone to unreadable handwriting, and fail to provide caretakers or guards with real-time visibility of which non-tenants are currently inside the premises visiting specific rooms. Furthermore, physical logs lack an accountability link between the visitor and the resident hosting them, creating a security gap in unauthorized access.

Solution: A targeted digital visitor management system that replaces physical logbooks with structured data entry, host-visitor verification, and digital ID photo uploads. It enables property managers to monitor active visitors in real-time and enforces building-specific policies—such as restricted holiday access for contractors—via external API integration. The system ensures building security and Staff accountability through role-based access, strict audit logging, and automated Admin notifications.

2.2 Core User Journeys

Journey 1: Logging a New Visitor (Check-In)

A Staff member logs into Vigilo using standard credentials or Google OAuth.

Click on "New Visitor Entry."

Enters visitor details (Name, Contact Number, Host Name, Visitor Type, Destination/Room, Purpose, Extended Visit) and uploads a photo of the visitor's ID.

Submit the form.

The system then saves the record with the current time and sets the visitor’s status as “Active”, and displays them on the Active Logs dashboard.

Journey 2: Processing a Departure (Check-Out)

Staff members view the "Active Logs" dashboard.

Locates the visitor record.

Click the "Check-Out" button.

The system records the exit timestamp, updates the visitor’s status to “Checked-Out”, removes the record from the Active Logs dashboard, and makes it available in the Historical Logs section for auditing.

Journey 3: Admin Voiding an Erroneous Record (RBAC & Email Integration)

A Staff member with the "Administrator" role logs into Vigilo.

Navigates from the Active Logs dashboard to the "Historical Logs" screen.

Locates a fraudulent or duplicated entry created by a security guard.

Clicks the "Void Record" action button and confirms the action.

The system updates the entry's status to "Voided" (performing a soft-delete to preserve the audit trail) and attaches the Admin's user ID to the record.

The backend automatically triggers an SMTP email to the Facility Manager summarizing the voided action for security oversight.

2.4 Detailed Feature Specifications

Visitor Status Lifecycle

To prevent ambiguous states, visitor records strictly follow these allowed status transitions:

[TABLE]

Current Status || Allowed Next Status || Trigger / Event
Active || Checked-Out, | Auto-Closed, | Voided || Visitor enters the premises.
Checked-Out || Voided || Staff manually checks out visitor.
Auto-Closed || Voided || Scheduled auto-close time is reached (default: 11:59 PM).
Voided || (Terminal State - None) || Admin flags record as invalid.

[/TABLE]

Feature: Staff Account Management

Screens: Admin Panel -> Create Staff Account

Fields: Full Name, Email Address, Role (Staff/Admin), Password

System Behavior:

Prevents Duplicate email address

Creates a new Staff record in the database

Password is securely hashed before storage using BCrypt.

Sends a welcome/verification email to the newly created user via SMTP.

Assigns selected role for access control

Role determines system permissions as follows:

Staff Role: Can log in, create visitor entries, View Active Logs, View Historical Logs, Process check-outs

Admin Role: Has all Staff permissions plus ability to create Staff accounts and void visitor records

Feature: Staff Authentication

Screens: Login Page.

Fields: Email, Password, or "Sign in with Google" button.

System Behavior:

Validates Staff credentials against the database or authenticates via Google OAuth.

The system will deny login if the Google account's email does not already exist in the users database (accounts must be pre-registered by an Admin)

Generates a custom JWT securely upon successful login (for both standard and OAuth methods).

Loads associated role and enforces role-based permissions

Grant access upon successful authentication

Denies access if credentials are invalid.

Feature: Visitor Entry Transaction

Screens: Dashboard / Entry Modal.

Data Collected: Full Name, Contact Number, Visitor Type (Guest/Employee/Contractor/Courier), Destination/Specific Room, Host Name (Tenant being visited), Purpose, Extended Visit boolean, and ID Attachment.

System Behavior:

Uploads and stores the attached file (image) on the server and links the file path to the database record

Creates new visitor record

Sets its status to “Active”

Sets time_in to Current Timestamp

Sets created_at to Current Timestamp

Records the visitor record created_by as Logged-in user ID.

Feature: Active Logs Dashboard

Screens: Main Dashboard.

Display: A data table showing only visitors whose status is 'Active'. Includes columns for Name, Time In, and an action button for Check-out.

External API Integration: Consumes a public API (e.g., Public Holidays/Events API) to display a banner at the top of the dashboard warning guards if today is a restricted access day.

Feature: Check-Out Processing

Screens: Main Dashboard.

System Behavior:

Updates the specific visitor’s database row

Sets status to “Checked-Out”

Sets time_out to Current Timestamp

Sets updated_at to Current Timestamp

Records updated_by as Logged-in user ID

Feature: Admin Log Management (Voiding)

Screens: Admin Dashboard / Log History.

Functions: Allows users with an Admin role to select a fraudulent or erroneous entry and can void records regardless of current status, soft-deleting the record to preserve the audit trail.

Access Control: Restricted to Administrator role only.

When voiding a record, the System:

Sets updated_at to Current Timestamp

Records updated_by as Logged-in Admin user ID

Sends an automated system notification email via SMTP to the facility manager summarizing the voided action.

Leaves the time_out field unchanged (e.g., remains NULL if the record was Active) to accurately preserve the original transactional state.

Feature: Scheduled Auto-Close Process

Process: Executes daily at a system-defined cut-off time (default: 11:59 PM).

System Behavior:

Identifies all logs where time_out IS NULL at 11:59 PM.

If is_extended_visit is false, the system automatically sets the time_out to 11:59 PM.

The system does not restrict late-night check-ins. Any non-extended visit that remains active at the scheduled cut-off time will be auto-closed, regardless of how recently it was created.

Sets the visitor status to "Auto-Closed".

Sets auto_closed = true and updated_by = "SYSTEM" to maintain data integrity and distinguish automated cleanups from manual staff check-outs.

Logic Rule: The is_extended_visit boolean acts as an "Exemption Flag" for the 11:59 PM cleanup.

Standard Behavior: For normal visitors, is_extended_visit is false; they are automatically transitioned to status = "Auto-Closed" at 11:59 PM.

Extended Behavior: If is_extended_visit is true, the record remains Active past midnight and must be manually checked out by staff.

2.5 Acceptance Criteria

AC-1: Successful Visitor Check-In

Given I am a logged-in Staff member

When I submit the new visitor form with valid details and a valid ID image file

Then the system stores the following:

time_in timestamp

created_by user ID

host_name

visitor_type_id

location_id

status = “Active”

file_url path

“Extended Visit = true (or false)”

And the visitor should appear on the Active Logs dashboard

AC-2: Successful Visitor Check-Out

Given I am viewing the Active Logs dashboard

When I click the "Check-Out" on a visitor record

Then that visitor should be removed from the active list

And the system must record the following:

time_out timestamp

updated_by user ID

status = “Checked-Out”

AC-3: Admin Log Voiding

Given I am logged in as an Administrator

When I flag a visitor entry as erroneous or fraudulent

Then the record's status should change to "Voided"

And the record remains stored for audit purposes

And the system sends a notification email via SMTP to the facility manager.

AC-4: Scheduled Auto-Close Process

Given there are visitor records with an "Active" status

When the system executes the scheduled auto-close process at the defined cut-off time

Then records not marked as “Extended Visit” are updated as follows:

status = “Auto-Closed”

time_out = 11:59 PM (system cut-off time)

Updated_by = SYSTEM

auto_closed = true

And they no longer appear in Active Logs.

AC-5: Google OAuth Login

Given I am a Staff member with a registered Google account

When I click "Sign in with Google" and authenticate

Then the system must verify my identity with Google

And generate a custom JWT for my session

And grant me access to the dashboard.

3.0 NON-FUNCTIONAL REQUIREMENTS

3.1 Performance Requirements

API response time: ≤ 2 seconds for 95% of requests under normal load

Web page load time: ≤ 3 seconds on standard broadband connection

System supports up to 100 concurrent authenticated users

Database queries for visitor search complete within 500ms

Scheduled Auto-Close process completes within 60 seconds

3.2 Security Requirements

HTTPS for all communications

Staff authentication implemented using secure JWT-based session management

Password hashing with BCrypt (salt rounds = 12)

Protection against SQL injection

Uploaded files must be validated to accept only safe image/document formats with a maximum file size of 5MB.

XSS protection via input sanitization and output encoding

Rate limiting enforced at 100 requests per minute per IP

Audit fields (created_by, updated_by, created_at, updated_at) must not be manually editable

3.3 Compatibility Requirements

Web Browsers: Chrome, Firefox, Safari, Edge (latest 2 versions)

Android: API Level 34 (Android 14) required for the mobile companion app using XML-Based UI Layouts.

Screen Sizes: Mobile (360px+), Tablet (768px+), Desktop (1024px+)

Operating Systems: Windows 10+, macOS 10.15+, Linux Ubuntu 20.04+

3.4 Usability Requirements

A new Staff user should be able to complete a visitor check-in within 3 minutes without training.

Interfaces must maintain a consistent navigation layout across all screens.

Error messages must clearly indicate the issue and provide recovery instructions if necessary.

Form validation errors must be displayed in real time before submission

Touch targets must be minimum 44x44px on mobile devices

System must support full keyboard navigation

4.0 SYSTEM ARCHITECTURE

4.1 Component Diagram

Technology Stack:

Backend: Java 17, Spring Boot 3.x, Spring Security, Spring Data JPA

Database: PostgreSQL 14+

Web Frontend: React 18, TypeScript, Tailwind CSS, Axios

Mobile: Kotlin, Retrofit

Build Tools: Maven (Backend), npm/yarn (Web), Gradle (Android)

Deployment: Supabase (Database), Render (Web), APK (Mobile)

Architecture Pattern:

The backend follows a Layered Architecture consisting of a REST Controller layer, Service layer (Business Logic), Repository layer (Spring Data JPA), DTO mapping layer, Security configuration, and Global Exception Handling. This ensures a strict separation of concerns, scalability, and code maintainability

6.0 DATABASE DESIGN

6.1 Entity Relationship Diagram

Detailed Relationships:

One-to-Many: Users → Logs: Each Staff member (Admin/Staff) is linked to the visitor records they create, ensuring full system accountability.

One-to-Many: Locations → Logs: Every visit is tied to a specific physical destination, allowing for granular tracking by room or office number .

One-to-Many: Visitor_Types → Logs: Provides a standardized lookup for categories such as Guest, Employee, or Contractor .

One-to-Many: Logs → Attachments: A single visit record can store multiple files, specifically the mandatory visitor ID images

Key Tables:

users: Stores Staff credentials, BCrypt hashed passwords, and assigned RBAC roles .

locations: A lookup table for specific facility areas, including room names, numbers, and floor levels.

visitor_types: Standardizes categories to prevent data duplication and ensure consistent reporting.

logs: The core business module storing visitor identity, automated timestamps, and visit status .

attachments: Maintains metadata and server paths for verified visitor ID file uploads .

Table Structure Summary:

users: id, email, password_hash, first_name, last_name, role, created_at.

locations: id, area_name, room_number, floor_level

visitor_types: id, type_name (e.g., Contractor, Courier).

logs: id, visitor_name, host_name, visitor_type_id (FK), location_id (FK), purpose, is_extended_visit (boolean), auto_closed (boolean), status, time_in, time_out, created_by (FK), updated_by (FK).

attachments: id, log_id (FK), file_url, file_type, uploaded_at .
